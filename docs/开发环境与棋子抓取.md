# 开发环境与棋子抓取基线

本文记录当前工作区用于棋子抓取的公开、可复现信息。它不是硬件安全认证，也不替代
真机说明书、急停测试、机械限位检查和手眼标定报告。

## 1. 已检查的开发环境

以下版本来自目标 Jetson 开发机和现有相关项目的只读检查：

| 项目 | 当前基线 |
| --- | --- |
| 硬件 | NVIDIA Jetson AGX Orin Developer Kit |
| 系统 | Ubuntu 22.04.5 LTS，aarch64 |
| 内核 | Linux 5.15.148-tegra |
| ROS 2 | Humble，安装在 `/opt/ros/humble` |
| Gazebo | Gazebo Sim Fortress，版本 6.18.0 |
| 构建工具 | CMake、Ninja、G++、CTest |
| CAN 工具 | `can-utils`，包括 `candump` / `cansend` |
| 仿真 CAN | `vcan0` 到 `vcan10`，共 11 路 |
| 仿真步长 | 0.01 s，即 100 Hz |

进入 ROS 2 环境：

```bash
source /opt/ros/humble/setup.bash
ros2 doctor --report
gz sim --versions
```

`gazebo_bot` 中已有环境检查和 vCAN 初始化脚本。相关项目检出后可运行：

```bash
cd "$ROBOT_WORKSPACE/gazebo_bot"
bash scripts/check_environment.sh
bash scripts/setup_vcan.sh
```

`ROBOT_WORKSPACE` 只是示例变量，实际路径按部署机器调整。不要把 SSH 地址、端口、
密钥文件路径、令牌或局域网拓扑写进 Git 仓库。

## 3. 棋盘和棋子仿真基线

当前 `gazebo_bot` 的棋盘配置是仿真默认值：

- 机器人基座为 `(0, 0, 0)`，面向世界坐标 `+X`。
- 棋盘中心为 `(0.70, 0.0)` m，棋盘上表面为 `z = 0.72` m。
- 棋盘格边长为 `0.05` m。
- 练习场景包含四个分散棋子：白兵 `c3`、白车 `f3`、黑象 `c6`、黑王 `f6`。
- 完整场景包含 32 个独立动态棋子；练习场景用于先验证感知、深度和夹爪姿态。
- 棋子碰撞体是为仿真稳定性做的近似，网格尺寸和质量不能直接当作真机棋子参数。

启动方式仍以 `gazebo_bot` 的脚本为准：

```bash
bash scripts/launch_gazebo.sh tiago-practice --headless
# 有桌面时可用 --gui
```

场景、格点世界坐标和棋子模型的机器可读来源分别是
`config/chess_scene.yaml`、`generated/chess_scene.yaml` 和 `models/chessaton_*`。
如果棋盘位置或格子尺寸改变，应重新运行 `scripts/generate_chess_scene.py`，不能只
手工修改生成文件。

## 4. 相机和坐标系

仿真中有一套头部 D435 和左右腕部 D405。当前名义话题如下：

| 相机 | 彩色图 | 深度图 | 点云/内参 |
| --- | --- | --- | --- |
| 头部 | `/tiago/head_front_camera/image` | `/tiago/head_front_camera/depth_image` | `/tiago/head_front_camera/points`、`/camera_info` |
| 左腕 | `/tiago/wrist_left_camera/image` | `/tiago/wrist_left_camera/depth_image` | `/tiago/wrist_left_camera/points`、`/camera_info` |
| 右腕 | `/tiago/wrist_right_camera/image` | `/tiago/wrist_right_camera/depth_image` | `/tiago/wrist_right_camera/points`、`/camera_info` |

这些是 Gazebo Transport 话题命名基线，接入 ROS 2 时需由 `ros_gz_bridge` 映射并实际
核对消息类型和 frame。相机外参目前是仿真名义值，不是真机测量值：

- 头部相机挂在 `head_2_link`，负责整盘观察、棋盘定位和粗定位。
- 左右腕部相机跟随 `arm_left_7_link` / `arm_right_7_link`，负责接近阶段的近距离
  对准和遮挡补偿。
- 规划和感知必须使用明确的 TF 链，至少检查 `base_link`、腕部相机 optical frame、
  夹爪抓取 frame 和棋盘 frame 是否在同一时间戳下可用。

真机落地前必须用棋盘格或 AprilTag 重新测量并验证：

```text
base_link -> head_front_camera_optical_frame
arm_*_7_link -> wrist_*_camera_optical_frame
gripper_*_grasping_frame -> TCP
```

## 5. 建议的抓取闭环

抓取不是“识别到棋子后发送一个关节角”。建议按以下阶段实现一个可取消的动作：

1. 头部相机拟合棋盘平面并识别棋子，输出棋子 ID、置信度、`PoseStamped` 和采样时间。
2. 用棋盘格先验和视觉结果得到源格中心；通过 TF2 转到 `base_link`，检查数据新鲜度。
3. 根据左右臂可达性、碰撞和腕部相机可见性选择执行臂，生成预抓取位姿。
4. 末端在棋子中心上方接近，垂直下降到棋盘上方约 2--3 mm 的安全高度，再闭合夹爪。
   夹爪目标位置/宽度必须来自真实夹爪配置，不要把仿真米制直线关节值直接套到真机。
5. 用夹爪反馈、末端位姿和腕部视觉确认夹持状态；确认前不要横向搬运。
6. 抬升到安全高度，移动到目标格，下降、释放，再后退并用头部相机验证棋子落点。
7. 任意阶段遇到 TF 过期、规划失败、限位、碰撞风险、反馈丢失或动作超时，都进入可观测
   的停止/失败状态，不自动重试真实运动。

仿真当前没有经过验证的接触力/夹持力传感器，因此“夹住”的判断只能先用夹爪状态、
棋子位姿和视觉复核组合；这不能宣称等价于真机力控成功。

## 6. 分阶段验收

### 阶段 A：只验证环境和感知

- `check_environment.sh` 通过，ROS 2、Gazebo、`can-utils` 可用。
- 练习场景能启动，头部和腕部图像/深度话题有数据。
- 棋盘平面和 64 个格点坐标与场景配置一致。
- 感知输出带 frame、时间戳、置信度，TF 查询失败时不会输出假位姿。

### 阶段 B：仿真运动

- 只使用 `vcan0..vcan10`，完成单关节、小幅度、夹爪和停止测试。
- 先做预抓取位姿和空动作，再做接触；每一步有碰撞/限位检查。
- 断开命令或超过运动看门狗时间后，机器人进入安全保持/停止状态。
- 记录目标位姿、实际反馈、动作结果、错误码和仿真时间，便于复现。

### 阶段 C：真机前置条件

- 完成 URDF、TCP、机械零点、关节限位、夹爪开度和相机外参的现场标定。
- 证明真机 CAN 协议、节点映射、反馈新鲜度和独立急停有效。
- 先做无棋子低速空载，再做单个轻质棋子，最后才扩大动作范围。
- 仿真协议、TI5 本体协议和灵巧手协议分别通过各自验收，不能互相猜测兼容。
