# TIAGo++ 接口协议与安全边界

本文件只记录 PAL TIAGo++ 仿真与 ROS 2 所需接口，避免把感知、Gazebo、仿真 CAN、
夹爪动作和控制台协议混成一层。带有“建议”的内容是 `zk_robot_ros` 尚待实现的
ROS 2 接口；带有“现有”的内容来自 TIAGo++ 相关项目的代码、配置和测试。

本次范围只包含 TIAGo++。其他机型和其他末端执行器协议不在本文定义范围内。

## 1. 总体分层

```text
头部/腕部 RGB-D
      │  ros_gz_bridge / ROS 2 sensor_msgs
      ▼
棋盘与棋子感知 ── TF2 ── MoveIt/规划 ── TIAGo++ 双臂/双夹爪执行
      │                                      │
      └──────────── 状态、结果、错误 ─────────┘
                       │
          Gazebo TIAGo++ 模型 + SocketCAN/vCAN

可选的 robot_station 只在上层发送控制意图，不能越过 ROS/机器人控制器直接写 CAN。
```

| 层 | 现有来源 | 用途 | 重要边界 |
| --- | --- | --- | --- |
| ROS 2 | 本仓库，尚待实现 | TIAGo++ 感知、TF、规划、动作、状态 | 不能把原始 CAN 帧当成感知接口 |
| Gazebo Transport | `gazebo_bot` | TIAGo++ 相机、模型和物理步进 | 通过 bridge 进入 ROS 2 后再供节点使用 |
| TIAGo++ 仿真 CAN v1 | `gazebo_bot` | 虚拟电机和 SocketCAN 闭环 | 只适用于 `vcan*`，不是实机标定协议 |
| TIAGo++ 执行器控制 | `zk_robot` | 现有 TIAGo++ 关节、机械臂和夹爪控制 | 本仓库只复用 TIAGo++ 相关实现 |
| ZRCP/1 | `robot_station` | 可选的 Web 控制台会话/控制权 | 当前仿真不依赖，也不是电机协议 |

## 2. TIAGo++ 仿真 CAN v1（现有）

来源：`gazebo_bot/docs/CAN_PROTOCOL.md` 和 `config/can_protocol.yaml`。

- Classical CAN 2.0、11 位标准帧、固定 8 字节、小端序。
- 命令 ID：`0x100 + node_id`；反馈 ID：`0x180 + node_id`；`node_id` 为 1--127。
- 命令数据：字节 0--3 为 `int32` 目标计数，4--5 为 `uint16` 最大速度，6 为命令码，
  7 为保留 flags。
- 命令码：`0x01` enable、`0x02` disable、`0x03` clear fault、`0x04` set zero、
  `0x10` position、`0x11` velocity、`0x12` stop、`0x20`/`0x21`/`0x22` 查询状态/位置/速度。
- 反馈数据：字节 0--3 为位置，4--5 为速度，字节 6 的 bit0/1/2 分别是 enabled、
  faulted、timed-out，字节 7 为故障码。
- 上电默认 disabled；有限关节越限会锁存故障并禁用；运动命令 500 ms 没有刷新会进入
  Hold/零速度状态。
- 编码器和减速比目前带有 `simulation_default` 标记，不能作为真实 TIAGo++ 的标定值。

最小原始帧示例：节点 1 的位置目标 `-256`、最大速度 `100`：

```text
CAN ID 0x101
DATA   00 FF FF FF 64 00 10 00
```

这套协议只服务于 `gazebo_bot` 的 TIAGo++ 虚拟电机。当前 ROS 2 仿真验证应固定使用
`vcan0..vcan10`，不应因为帧格式相似就把它发送到真实接口。

## 3. robot_station 的 ZRCP/1（可选，不属于当前仿真必需项）

`robot_station/doc/机器人控制台通信协议.md` 定义的是控制台到机器人服务的应用层协议：

- TCP 使用 4 字节大端无符号长度前缀，后跟 UTF-8 JSON；WebSocket 只承载浏览器意图，
  不直接发送机器人 TCP 帧。
- 使用 `system.hello`、控制租约、心跳、动作 ID、绝对期限和 `motion.stop_all`。
- 网关 ACK 只表示请求被协议层接受；真实到位、反馈新鲜度、故障和最终结果必须来自
  TIAGo++ 控制器状态/结果消息。
- 软件停止不能替代硬接线急停；TIAGo++ 控制器必须有独立的控制线程和看门狗。
- 浏览器、网关和 ROS 2 节点都不应直接获得或拼接原始 CAN 帧。

如果以后让控制台触发棋子抓取，建议路径是：

```text
robot_station (ZRCP/1) -> ROS 2 抓取 action -> TIAGo++ 规划/执行器 -> TIAGo++ CAN
```

当前仿真也可以完全跳过 `robot_station`，由 ROS 2 action 直接调用 TIAGo++ 执行器。

## 4. 建议冻结的 ROS 2 接口

以下是本仓库后续实现时的建议，不表示当前已经存在这些 topic/action：

| 接口 | 类型 | 语义 |
| --- | --- | --- |
| `/chess/board_pose` | `geometry_msgs/PoseStamped` | 棋盘平面和坐标系 |
| `/chess/piece_poses` | 自定义消息或 `PoseArray` 扩展 | 棋子 ID、颜色/类型、位姿、置信度、时间戳 |
| `/tiago/*_camera/{image,depth_image,points,camera_info}` | `sensor_msgs` | TIAGo++ bridge 后的相机数据 |
| `/tf`、`/tf_static` | `tf2_msgs` | TIAGo++、相机、棋盘和棋子的坐标转换 |
| `/<arm>/grasp_piece` | `zk_robot_msgs/action/GraspPiece` | 接近、闭合、抬升、搬运、释放的可取消动作 |
| `/<arm>/gripper_command` | `control_msgs/action/GripperCommand` 或适配动作 | TIAGo++ 夹爪目标和反馈 |
| `/tiago/state`、`/tiago/fault` | 自定义状态/事件消息 | TIAGo++ 执行器状态、反馈新鲜度、故障和停止原因 |

`GraspPiece` 至少应包含源/目标格或位姿、选择的 TIAGo++ 手臂、预抓取高度、夹爪目标
和超时；反馈应包含 `perception / planning / approaching / closing / lifting /
placing / verifying / stopping` 阶段；结果应包含明确错误码，不能只返回一个 `bool`。

## 5. 安全与验收边界

1. 开发和自动化验证只允许 `vcan0..vcan10`；脚本应主动拒绝真实 `can0`。
2. 真实 TIAGo++ 运动前必须有独立急停、硬件使能、机械限位、零位和通信失联保护；网页停止
   和 ROS 2 action cancel 都只是软件请求。
3. 一台 TIAGo++ 同一时刻只能有一个运动控制者；感知、规划和控制台不能分别抢占同一轴。
4. 所有运动命令都要检查状态新鲜度、绝对超时、速度/位置限位、碰撞风险和取消传播。
5. 任何失败都要保留目标、实际反馈、错误码、时间戳和停止原因；不能用目标值冒充当前位置。
6. 仿真通过后，真实 TIAGo++ 必须按“无棋子低速空载 -> 单棋子 -> 完整流程”逐级验收；不能
   把仿真的质量、摩擦、相机外参、编码器换算或夹爪行程直接复制到实机。

### 当前仍需补齐的 TIAGo++ 资料

- TIAGo++ ROS 2 控制器、MoveIt/ros2_control 和 Gazebo bridge 的确切版本。
- 夹爪动作接口、开度单位、反馈字段和夹持确认方式。
- 棋盘/棋子检测消息的 ID、置信度、时间戳和坐标系定义。
- 头部/腕部相机的 ROS 2 消息类型、内参、外参和有效深度范围。
