# 接口协议与安全边界

本文件把已有项目中的协议分层记录下来，避免把 ROS 2、Gazebo、仿真 CAN、TI5 真机
CAN 和控制台 TCP 当成一套协议。带有“建议”的内容是 `zk_robot_ros` 尚待实现的
ROS 2 接口；带有“现有”的内容来自相关项目的代码、配置和测试。

## 1. 总体分层

```text
头部/腕部 RGB-D
      │  ros_gz_bridge / ROS 2 sensor_msgs
      ▼
棋盘与棋子感知 ── TF2 ── MoveIt/规划 ── 机械臂/夹爪执行器
      │                                │
      └──────────── 状态、结果、错误 ────┘
                       │
          仿真：gazebo_bot + vCAN
          真机：zk_robot + 实际 CAN/夹爪协议

可选的 robot_station 只在上层通过 ZRCP/1 发控制意图，不能越过 ROS/机器人控制器直接写 CAN。
```

| 层 | 现有来源 | 用途 | 重要边界 |
| --- | --- | --- | --- |
| ROS 2 | 本仓库，尚待实现 | 感知、TF、规划、动作、状态 | 不能把原始 CAN 帧当成感知接口 |
| Gazebo Transport | `gazebo_bot` | 仿真相机、仿真模型和物理步进 | 通过 bridge 进入 ROS 2 后再供节点使用 |
| 仿真 TIAGo CAN v1 | `gazebo_bot` | 虚拟电机和 SocketCAN 闭环 | 只适用于 `vcan*`，不是实机协议 |
| TI5 本体 CAN | `zk_robot` | T170C 真机关节 | 与仿真 CAN v1 不兼容，按真机配置/记录核对 |
| 傲意手协议 | `zk_robot` | 左右灵巧手 | 独立于 TI5 本体协议，不能套用本体发现帧 |
| ZRCP/1 | `robot_station` | Web 控制台到机器人服务的会话/控制权 | 不是电机协议，也不替代实体急停 |

## 2. 仿真 TIAGo CAN v1（现有）

来源：`gazebo_bot/docs/CAN_PROTOCOL.md` 和 `config/can_protocol.yaml`。

- Classical CAN 2.0、11 位标准帧、固定 8 字节、小端序。
- 命令 ID：`0x100 + node_id`；反馈 ID：`0x180 + node_id`；`node_id` 为 1--127。
- 命令数据：字节 0--3 为 `int32` 目标计数，4--5 为 `uint16` 最大速度，6 为命令码，
  7 为保留 flags。
- 命令码：`0x01` enable、`0x02` disable、`0x03` clear fault、`0x04` set zero、
  `0x10` position、`0x11` velocity、`0x12` stop、`0x20`/`0x21`/`0x22` 查询状态/位置/速度。
- 反馈数据：字节 0--3 为位置，4--5 为速度，字节 6 的 bit0/1/2 分别是 enabled、
  faulted、timed-out，字节 7 为故障码。
- 上电默认 disabled；有限关节越限会锁存故障并禁用；运动命令 500 ms 没有刷新会进入
  Hold/零速度状态。
- 编码器和减速比目前带有 `simulation_default` 标记，不能作为 PAL/TI5 真机标定值。

最小原始帧示例：节点 1 的位置目标 `-256`、最大速度 `100`：

```text
CAN ID 0x101
DATA   00 FF FF FF 64 00 10 00
```

这套协议服务的是 `gazebo_bot` 的虚拟电机。任何真机接入前都必须有独立的节点、帧、
波特率、编码器和安全状态验证，不能因为字段相似就直接发送到 `can0`。

## 3. TI5 T170C 本体 CAN（现有，但必须按真机复核）

`zk_robot` 当前实现/测试显示，本体使用 1 Mbps Classical CAN、按设备节点 ID 通信，
并通过发现阶段建立逻辑总线与 `canX` 的映射。当前已在代码测试中覆盖的操作包括：

| 操作 | 命令/字段 | 说明 |
| --- | --- | --- |
| 当前位置查询 | `0x08` | 发现阶段使用，只读 |
| 运行模式查询 | `0x03` | 读取驱动器运行模式 |
| 故障位查询 | `0x0A` | 读取原始故障位 |
| 位置范围查询 | `0x1A` / `0x1B` | 读取正/负目标范围 |
| Position CSP | `0x44` | 当前已确认的实时位置控制路径 |
| Stop 模式 | 数据 `0x02` | 进入停止模式 |
| 清故障 | 数据 `0x0B` | 清除后仍需重新进入安全控制流程 |
| Profile Position | `0x1E` | 已有编码/测试，但不等于已开放全部实机运动能力 |

本体协议与仿真协议的差异很大：本体的发现、反馈新鲜度、总线健康、软件限位和独占
控制都由 `zk_robot` 的 TI5 层负责。本仓库的 ROS 2 执行器应调用明确的机器人适配层，
不要让感知节点或网页直接构造上述帧。

## 4. 傲意灵巧手协议

左右手虽然也走 SocketCAN，但使用独立的 `aoyi_hand` 协议，不参与本体的 `0x08` 节点
发现和 `0x44` 位置控制。当前 `zk_robot/config/ti5/t170c/hands.yaml` 有左右手的
接口和控制器节点配置，但文档同时说明完整反馈格式、异常行为和现场接口仍要继续实机
确认。

因此 ROS 2 侧应抽象成“夹爪/手控制器”能力和状态，例如开度、目标、运动中、故障、
反馈时间戳和夹持确认，不向上暴露某个厂商的原始帧字段。没有力/接触反馈时，抓取成功
只能标记为“运动完成且视觉/位姿复核通过”，不能伪称为力控确认。

## 5. robot_station 的 ZRCP/1（可选上层协议）

`robot_station/doc/机器人控制台通信协议.md` 定义的是控制台到机器人服务的应用层协议：

- TCP 使用 4 字节大端无符号长度前缀，后跟 UTF-8 JSON；WebSocket 只承载浏览器意图，
  不直接发送机器人 TCP 帧。
- 使用 `system.hello`、控制租约、心跳、动作 ID、绝对期限和 `motion.stop_all`。
- 网关 ACK 只表示请求被协议层接受；真实到位、反馈新鲜度、故障和最终结果必须来自
  机器人端状态/结果消息。
- 软件停止不能替代硬接线急停；机器人端必须有独立的控制线程和看门狗。
- 浏览器、网关和 ROS 2 节点都不应直接获得或拼接原始 CAN 帧。

如果以后让控制台触发棋子抓取，建议路径是：

```text
robot_station (ZRCP/1) -> ROS 2 抓取 action -> 规划/执行器 -> 真机适配层 -> CAN/手协议
```

而不是让 `robot_station` 绕过 ROS 2 直接调用 CAN。

## 6. 建议冻结的 ROS 2 接口

以下是本仓库后续实现时的建议，不表示当前已经存在这些 topic/action：

| 接口 | 类型 | 语义 |
| --- | --- | --- |
| `/chess/board_pose` | `geometry_msgs/PoseStamped` | 棋盘平面和坐标系 |
| `/chess/piece_poses` | 自定义消息或 `PoseArray` 扩展 | 棋子 ID、颜色/类型、位姿、置信度、时间戳 |
| `/tiago/*_camera/{image,depth_image,points,camera_info}` | `sensor_msgs` | bridge 后的相机数据 |
| `/tf`、`/tf_static` | `tf2_msgs` | 机器人、相机、棋盘和棋子的坐标转换 |
| `/<arm>/grasp_piece` | `zk_robot_msgs/action/GraspPiece` | 接近、闭合、抬升、搬运、释放的可取消动作 |
| `/<arm>/gripper_command` | `control_msgs/action/GripperCommand` 或适配动作 | 夹爪目标和反馈 |
| `/robot/state`、`/robot/fault` | 自定义状态/事件消息 | 执行器状态、反馈新鲜度、故障和停止原因 |

`GraspPiece` 至少应包含源/目标格或位姿、选择的手臂、预抓取高度、夹爪目标和超时；
反馈应包含 `perception / planning / approaching / closing / lifting / placing /
verifying / stopping` 阶段；结果应包含明确错误码，不能只返回一个 `bool`。

## 7. 安全与验收边界

1. 开发和自动化验证只允许 `vcan0..vcan10`；脚本应主动拒绝真实 `can0`。
2. 真实运动前必须有独立急停、硬件使能、机械限位、零位和通信失联保护；网页停止和
   ROS 2 action cancel 都只是软件请求。
3. 一台机器人同一时刻只能有一个运动控制者；感知、规划、控制台不能分别抢占同一轴。
4. 所有运动命令都要检查状态新鲜度、绝对超时、速度/位置限位、碰撞风险和取消传播。
5. 任何失败都要保留目标、实际反馈、错误码、时间戳和停止原因；不能用目标值冒充当前位置。
6. 仿真通过后，真机必须按“无棋子低速空载 -> 单棋子 -> 完整流程”逐级验收；不能把仿真
   的质量、摩擦、相机外参、编码器换算或夹爪行程直接复制到实机。

- 棋盘和棋子的实测尺寸、质量、摩擦与碰撞安全间隙。
- 真实 CAN 接口/节点映射、驱动器固件版本和厂商协议确认记录。
- 头部/腕部相机内参、外参和有效深度范围。
- ROS 2 发行版中使用的 Gazebo bridge、MoveIt/控制器版本。
